# Internationalisation

Every line the skill shows the user lives here. The skill picks a key,
renders the value for `session.language`, and substitutes any `{var}`
placeholders. There is no on-the-fly translation; both languages are
hand-written and reviewed by legal / compliance.

## Language picker (Entry A only)

Set `session.language` from the first user message:

- If the message contains any CJK character (`/[一-鿿]/`) → `zh`.
- If the message is dominantly ASCII alphabetic and contains a known
  trigger token (`KYA`, `deposit`, `withdraw`, etc.) → `en`.
- If the message is unparseable (URL only, emojis only, very short
  keyword) → default to `en` and let the user switch via the `language`
  command if they prefer `zh`.

After Entry A, `session.language` is persisted server-side. The user can
switch mid-session with the `language` command, but the default stays
sticky across resume.

## Mid-session switch

The `language` command updates `session.language` and re-renders the
current step in the new language. Already-emitted output is not
retroactively translated. The server logs the switch for audit (so a
reviewer can see "user typed module 2 answers in zh, then switched to
en mid-Module-3" if it matters).

## String keys

Each entry is `{ en, zh }`. Substitution variables use `{name}` syntax.

## Why strings live here, not inline

- Translation review. Compliance and legal want to read the full bilingual
  text in one place, not chase it across seven markdown files.
- Drift prevention. The same line shouldn't be paraphrased in two places.
  When the regulator asks for a wording change, there's exactly one file
  to grep.
- A/B and regional variants. If a future iteration needs `zh-TW` or
  `en-GB`, the picker rule and the key table are the only things to
  extend.
